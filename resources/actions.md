# 快捷命令提示词

编辑器与资源管理器右键「快捷命令」子菜单的五个动作。`{{target}}` 会被替换为目标描述
（工作区相对路径与行号范围，如 `example.ts（第 12-30 行）`），其余内容原样发往 CodeBuddy。

格式约定：

- `## 动作键` 起一段，键名与 `src/modules/commands/actionRegistry.ts` 中的引用一一对应；
- 正文放在标记为 `text` 的代码块内，可多次出现 `{{target}}`；
- 文案直接决定模型行为，修改时保持「先界定范围、再给步骤、最后写禁止项」的结构。

## fix

```text
请修复以下代码中的问题：{{target}}

1. 先完整阅读该文件及其调用方，定位问题的真实成因，不要只改报错表象；
2. 改动保持最小必要范围，不顺手重构，不调整无关格式；
3. 遵循仓库现有约定（命名、错误处理、类型），复用已有的工具函数与类型，不要新增重复实现；
4. 完成后逐项说明改了什么、为什么这样改，以及是否存在需要我确认的取舍；
5. 若问题无法在当前范围内安全修复，先说明原因并给出方案，不要强行改动。

不要引入新的依赖，不要修改与问题无关的文件。
```

## review

```text
请审查以下代码：{{target}}

1. 逐项检查正确性（边界条件、空值、异常处理）、安全性（注入、越权、敏感信息泄露）、并发与资源释放；
2. 指出问题时给出文件与行号、具体成因，并区分「必须修」与「建议优化」；
3. 本轮只做审查，不要修改任何文件；
4. 若发现严重问题，给出最小可行的修复方案供我确认。
```

## optimize

```text
请对以下代码做系统性审查与优化：{{target}}

从「逻辑正确性、安全防御、边界鲁棒性、性能效率」四个维度排查，按三步推进。

## 第一步：分析

逐项对照下面的检查清单，给每个问题打级别标签：

- critical（必须修复）：逻辑错误、安全漏洞、数据损坏风险、用户可见的功能异常；
- minor（建议优化）：边界未处理、性能低效、代码异味、可维护性欠缺；
- suggestion（仅供参考）：风格偏好、轻微重构机会，只标注不修改。

检查清单：

1. 导入与顶层声明：未使用的导入/变量；仅作类型的导入用 import type；固定配置/枚举提取为模块级常量（UPPER_SNAKE_CASE）；循环依赖只标注不修改。
2. 类型系统：参数与返回值显式标注；禁止 any，必要时用 unknown + 类型守卫；审视 as 断言与非空断言是否有必要；组件 Props 用「组件名 + Props」命名；避免 Record<string, any>。
3. React Hooks：useState 初始值合理；useEffect 依赖完整；异步请求需清理，避免卸载后 setState；useCallback/useMemo 仅在确有收益时使用；检查闭包捕获的过时值；禁止在循环/条件/嵌套函数中调用 Hooks。
4. 数据流与状态：能下放的状态不上升；衍生值用 useMemo 而非 state；避免多个关联 state 不同步；数组/对象状态用不可变方式更新；受控与非受控写法保持一致。
5. 性能：列表 key 稳定且唯一；高频事件（scroll/resize/input）加防抖或节流；昂贵计算缓存；非首屏模块可用 React.lazy + Suspense；避免渲染期创建对象/数组字面量。
6. 安全：禁止未经清洗的 dangerouslySetInnerHTML；动态拼接的 URL/路径需校验；日志、注释、错误消息不得泄露 token、密钥、内部路径；权限不能只靠前端判断。
7. 边界处理：null/undefined/空数组要有兜底与空状态；网络与异常分支要有友好提示；极端输入（超长字符串、负数、NaN、超大数组）要有防御；连续操作防竞态；监听、定时器、observer 在卸载时释放；数值运算做 isNaN/isFinite/除零保护。
8. 代码品质：函数超过 40 行考虑拆分；组件超过 150 行考虑拆子组件或自定义 Hook；深层嵌套用早返回扁平化；重复 3 次以上的片段提取复用；注释解释业务规则与权衡而非复述代码；同一概念命名一致。
9. TypeScript：不绕过 strict 检查；泛型加 extends 约束；优先 as const + 联合类型而非 enum；类型收窄用类型守卫而非 as。

## 第二步：解释

对每个要修复的问题说明：根因与触发条件、影响场景；修复方案与 1-2 个替代方案；涉及的原则（防御式编程、单一职责、命令查询分离等）；修复后的正确性/性能/可维护性收益。

## 第三步：修复

- 一处问题一次改动，仅改有问题的行，不重构相邻代码、不改注释格式；
- 保持与文件现有风格一致（缩进、引号、分号、换行）；
- 先修 critical，再修 minor，suggestion 只标注；
- 能用原有工具函数就复用，不新增重复实现；
- 改完确认无新增 lint 错误，3 次内无法消除就停下询问我；
- 涉及方案取舍或可能改变外部行为的，先给出方案，经我确认后再改。

## 输出模板

### [级别] 问题简述

位置：文件:行号；根因：…；影响：…；修复方案：…；替代方案：…；涉及原则：…；改进收益：…
```

## style

```text
请按以下编码规范检查并修正：{{target}}

仅修改违反规则之处，不改动任何业务逻辑；整体保持 4 空格缩进、单引号。

1. 分号：语句结尾不使用分号。
2. import 顺序：builtin（Node 内置）→ external（npm 包）→ internal（@apps/**、@backend/**、@components/**、@modules/**、@public/**、@shared/** 等别名）→ sibling（./ 相对路径）→ index（./index）→ type（import type）。组间不留空行，组内按字母升序且忽略大小写，类型导入统一置于最后。
3. 命名：变量/函数 camelCase（React 组件允许 PascalCase）；类型 PascalCase 且不加 I 前缀；布尔变量带 is/has/can/should/did/will 前缀；枚举成员 UPPER_CASE；类成员 camelCase，私有靠 private 修饰符；未使用的变量与参数允许 _ 前缀。
4. React Hooks：允许手动使用 useMemo/useCallback，遵循 react-hooks 推荐规则，useEffect 依赖数组必须完整。
5. 客户端指令：含 JSX 且使用 hooks/DOM/浏览器特性的文件，首行必须是 'use client'。

完成后通读一遍，确认没有引入新的违规，并列出实际修改项。
```

## refactor

```text
请分析以下代码的结构，找出可以提取为独立函数或模块的部分：{{target}}

从四个维度分析：

1. 职责分离：找出职责过多、承担超出自身范围的函数/组件，判断可拆分的逻辑边界；
2. 复用性：找出跨模块重复的代码模式，判断是否值得提取为公共工具函数或自定义 Hook；
3. 复杂度：找出圈复杂度过高的函数（分支过多、嵌套过深），判断能否用早返回或提取辅助函数简化；
4. 耦合度：找出模块间不合理的直接依赖，判断能否用依赖注入或事件解耦。

本轮只输出分析结论，不要改动任何文件。每个重构点按以下结构给出：

### 建议的函数名 / 文件名

- 提取理由：降低复杂度 / 提高复用性 / 职责分离；
- 来源：文件路径:行号；
- 建议签名：函数名、参数、返回值；
- 文件路径：可跨模块共享的工具函数放 shared/utils/xxx.ts，仅当前模块使用放当前目录 utils/；自定义 Hook 同理（hooks/ 或 apps/src/hooks/）；页面结构组件放当前页面目录 layout/；
- 重构步骤：创建新文件 → 迁移逻辑 → 更新调用处 → 验证功能一致。

若某个重构点会改变对外行为或涉及跨模块契约，先说明风险并等我确认。
```
