# 2026-10-31 工作记录

## 修改内容摘要

新建 VSCode 扩展 `webian-prompt`（微边提示词），用于 AI 提示词管理：

1. 技术栈落地：TypeScript 7.0.2 + React 19.3.1 + Vite 8 + Tailwind CSS 4（CSS-first `@theme`）+ shadcn/ui 风格组件 + Lucide。
2. 逆向确认 CodeBuddy 4.12 的内部命令通道：`tencentcloud.codingcopilot.sendToChat`（handler 接收 `{ prompt, mode }`，内部 `autoSend: true` + 新建对话），由 `CommandRegistry` 统一注册；命令 ID 前缀来自 `COMMAND_ID_PREFIX = 'tencentcloud.codingcopilot.'`。
3. 扩展宿主：`CodeBuddyBridge` 实现「focus 聊天视图激活扩展 → 校验命令存在 → 发送」链路，含剪贴板降级；`PromptStore` 基于 globalState 持久化并做归一化；`PromptSidebarProvider` 承载 Webview、CSP nonce 与消息路由。
4. 侧边栏 UI：提示词卡片（发送 / 复制 / 编辑 / 上移下移 / 删除）、搜索、新增与编辑对话框、CodeBuddy 连接状态提示、Toast。
5. 右键菜单「微边代码」：`/fix <相对路径>` 与 `/cr <相对路径>`，有选区时追加行号范围。
6. 内置四条预设提示词：提交到 Git、推送到 Git、按顺序实施、按推荐实现。

- `tsconfig.json` 在 TS 7 下必须移除 `baseUrl`，`paths` 需写 `./` 前缀的相对路径。

## css-lcurlyexpected 真正成因（重要）

- 上述 19 条 `css-lcurlyexpected` 的真实触发点是**文件头部注释里出现了完整的 at-rule 关键字 `@theme` 文本**。
  Tailwind 语言服务不跳过注释内容，把注释里的 `@theme` 当作真实指令解析，导致 `:root` 块起整篇状态错乱，
  报错位置落在块内各条自定义属性上（列号指向 `var` 首字母），换文件 URI 后依然复现。
- 定位方式：最小可复现文件逐段加回。`@theme` / `@theme inline` / `oklch()` / 嵌套 `var()` / 属性选择器 /
  `::-webkit-scrollbar` / 中文注释本身均无问题，唯独注释含 at-rule 关键字时必现。
- 规避约定：本项目 CSS 注释中不得写出完整 at-rule 关键字（用「主题块」「导入语句」等中文描述代替），
  已在文件头部注释中注明。

## 面板空白排查

- 现象：侧边栏标题栏按钮正常，Webview 区域完全空白。
- 已排除：`dist/webview/app.js`（759KB）与 `app.css` 均存在；产物是自执行 IIFE，无顶层 import/export、无 `eval` / `new Function`，`import(` 只出现在 React 的 `lazy` 报错文案里；`lucide-react` 1.65.0 中 `RotateCcw` 等图标全部存在；宿主日志无激活失败记录。
- 日志噪音：`... created a webview without a content security policy` 每次激活都会出现，但 `Tencent-Cloud.coding-copilot` 自身也报同一条，说明是该版本对 webview 的普遍误报，不能作为根因。
- 已加启动诊断：HTML 的 `#root` 内置「正在加载提示词面板…」占位，并在外部脚本之前注册 `error`（捕获阶段，含资源加载失败）与 `unhandledrejection`，把失败原因直接渲染到面板。据此可区分「脚本没被加载」与「脚本运行时报错」。
- 诊断结论：面板回显「脚本异常：Uncaught ReferenceError: process is not defined」。
- 根因：`vite build` 走的是 **library 模式**，Vite 在该模式下不替换 `process.env.NODE_ENV`（库应由使用方决定环境）；产物里 react-dom 的入口判断 `process.env.NODE_ENV === "production" ? prod() : dev()` 直接引用 `process`，webview 是浏览器环境没有该全局，bundle 初始化即抛 ReferenceError，整棵 React 树未挂载。
- 修复：`vite.config.mts` 改为 `defineConfig(({ mode }) => ...)` 并显式 `define: { 'process.env.NODE_ENV': JSON.stringify(mode === 'production' ? 'production' : 'development') }`。
- 验证：产物中 `process.env` 出现 0 次；剩余 6 处 `process` 全在 `typeof process === "object"` 守卫内，短路安全。产物由 759KB 降到 327KB——此前打进的是 development 版 React。
- 结论沉淀：webview 的 library 构建必须显式 define `process.env.NODE_ENV`，否则白屏且宿主日志无任何报错，只能靠 HTML 内诊断脚本捕获。
- 复发与真凶：修完重载后仍报同一错。检查发现 `dist/webview/app.js` 又变回 759KB、`process.env` 12 处，写入时间晚于修复构建。定位到 PID 10776 的 `concurrently`（21:21 启动，早于 21:43 的配置修改）：`vite build --watch` 未重载新配置，任何源码变动都会用旧配置重新打包并覆盖产物。
- 处理：终止该 watch 进程 → `build:webview` 重建（327KB、`process.env` 0 处）→ `build:extension` 重建。
- 教训：修改 `vite.config.mts` / `scripts/esbuild.mjs` 等构建配置后，必须重启 `pnpm run watch`，否则监听进程会持续用旧配置覆盖产物，表现为「修复无效」。

## 「未检测到 CodeBuddy 发送命令」的成因与修复

- 提示来源：`pushState()` 调用 `isSendCommandAvailable()`，即 `commands.getCommands(true)` 是否包含 `tencentcloud.codingcopilot.sendToChat`。

- 真实风险：原先 `ACTIVATION_SETTLE_MS = 400` 固定 sleep，而日志显示 CodeBuddy 激活耗时约 2.5s，首次点击极易真的降级到剪贴板。
